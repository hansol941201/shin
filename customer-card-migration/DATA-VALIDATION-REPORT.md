## 1. 데이터 기준일에 관한 중요한 사실

원본 사이드바의 **“최종 업데이트”** 는 저장된 값이 아닙니다.

```js
document.getElementById('lastUpdate').textContent = new Date().toLocaleDateString('ko-KR');
```

접속한 날의 날짜를 그대로 출력하므로 **언제 접속해도 “오늘”로 보입니다.** 데이터 기준일로 사용할 수 없습니다.
대신 다음 두 값을 기준으로 삼았습니다.

| 기준 | 값 | 근거 |
|---|---|---|
| `sourceUpdatedAt` | 2026-07-23 | 저장소 최신 커밋(배포)일 |
| 데이터 내 최신 날짜 | 2026-05-06 | 전 업체 타임라인 중 가장 늦은 날짜 |

경과일(`mou.elapsedDays`)은 **2026-09-02 기준**으로 계산했습니다.

### 3-1. 레거시 관리 엑셀 반영


원본 대시보드가 생기기 전에 쓰던 관리 엑셀 «461ca6f3-_______26.04.28.xlsx» 을 받아 MOU 체결 근거를 확인했습니다.

**이 엑셀에서 확인된 것**

| 항목 | 내용 |
|---|---|
| 협약업체 명부 | `보고!B2` = “전체 협약업체”, `보고!K2` = 257개사 |
| 명부 등재 업체 | 257개사 (전건 이번 데이터와 매칭됨) |

| 그 시트의 체결일 | 129건 |

**등급 정의 자체가 협약 체결을 전제합니다.** `C = 협약유지(미가동)`, `N = 협약 체결 1년 6개월 미만`,
`B = 1~2회 사용`, `F = 이슈 고객(이탈)` — 모두 협약이 이미 맺어져 있어야 성립하는 등급입니다.
따라서 **등급 표에 올라 있으면 협약이 체결된 업체**라는 문서 근거가 됩니다.

**처리 결과**

| 항목 | 건수 |
|---|---|
| `기존 협력업체·MOU 상태 확인 필요` → `MOU 체결 완료·체결일 미확인` 이전 | **60** |

### 단계를 건너뛴 것은 오류로 보지 않습니다

미팅 없이 바로 체결하거나 1차 미팅을 건너뛰고 체결하는 업체가 실제로 있습니다.
따라서 **체결이 확인된 업체는 중간 단계 날짜가 비어 있어도 오류로 표시하지 않습니다.**
대신 어떤 단계에 날짜 기록이 없는지를 `mou.skippedSteps` 에 참고 정보로만 남겼습니다
(해당 업체 **45개사**).

## 8. MOU 체결일 불일치 — 출처 우선순위로 확정

### 확정 규칙

| 우선순위 | 출처 |
|---|---|
| 1 | **체결 완료** 메뉴의 MOU 체결일 |

| 4 | 기타 화면 · 비고에 기록된 날짜 |

## 10. 수집하지 못한 정보와 사유

### 1. 레거시 관리 엑셀 — 반영됨

**사유** — 사용자가 제공한 «461ca6f3-_______26.04.28.xlsx» 에서 MOU 체결 근거를 추출해 반영했습니다. 이 엑셀은 등급 표에 오른 업체 전체를 "전체 협약업체"(257개사, 보고!B2 / 보고!K2)로 집계합니다.

**영향** — 협약 명부 근거로 60개사를 '기존 협력업체·MOU 상태 확인 필요' → 'MOU 체결 완료·체결일 미확인' 으로 옮겼습니다. 다만 이 엑셀에도 해당 업체들의 체결일은 없어 날짜는 추정하지 않고 미확인으로 두었습니다. 체결일이 적힌 시트는 신규업체 CRM / 신규업체 CRM 26년 뿐입니다.

### 2. Firebase 실시간 동기화 데이터 (사용자가 화면에서 수정·추가한 최신분)

**사유** — 원본 사이트는 정적 시드 위에 Firebase Realtime Database(pour-partner-dashboard…asia-southeast1)와 브라우저 localStorage 값을 덮어써서 표시합니다. 이 빌드를 만든 작업 환경에서는 해당 도메인이 네트워크 정책으로 차단되어 접근할 수 없었습니다.

**영향** — 이 스냅샷은 GitHub Pages 에 배포된 공개 정적 기준값입니다. 목록 화면의 [원본과 동기화] 버튼을 누르면 최신 수정분까지 받아옵니다.

### 3. 허들·보류 “액션 결정” (재접근 / 종결 / 보류 유지 / 재발송 / 확인 필요)

**사유** — 원본에서 localStorage 키 hurdleActions 에만 저장되며 GitHub Pages 배포 데이터에 포함되지 않습니다. 목록 화면의 [원본과 동기화] 버튼으로 Firebase 에서 직접 받아올 수 있습니다.

**영향** — 허들·보류 20개사 전건 hold.decision = "결정 미입력".

### 4. 담당자(1차·2차 미팅 담당자, 내부 담당자) 및 담당자 연락처

**사유** — 시드 데이터에 m1Owner/m2Owner 필드가 존재하지 않습니다(런타임에 null 로 생성). 커리큘럼 문서에 팀 단위 담당(영업팀·김수진·신명희)만 있고 업체별 매핑은 없습니다.

**영향** — manager.* 전건 null. 카드에서는 “미확인”으로 표시.

### 5. 1차·2차 미팅 “예정일”

**사유** — 시드에 m1Scheduled/m2Scheduled 필드가 없습니다(런타임 null). 일부 업체는 자유 텍스트(“일정 조율중(05.21)”, “조율중”, “양산지사 예정”)만 존재하여 mou.rawLabels 에 원문 그대로 보존했습니다.

**영향** — firstMeetingScheduledAt / secondMeetingScheduledAt 전건 null.

### 6. 업체별 MOU 자료 관리 체크리스트 (제출 서류 체크 상태)

**사유** — localStorage 키 companyDocs_<업체명> 에만 저장됩니다. 체크리스트 “정의”는 공개되어 있어 meta.checklistDefinition 으로 포함했습니다.

**영향** — documents 전건 빈 배열.

### 7. 현장 상세 날짜 (카달로그 요청일·기술자문·컨설팅·PT·공고·낙찰·진행일)

**사유** — 시드의 현장 정보는 구버전 자유 텍스트(c.site)뿐이고 구조화된 siteRecords 는 localStorage/Firebase 에만 있습니다. 텍스트 안의 “23.7/20” 같은 표기는 연도가 생략된 경우가 많아 날짜로 확정할 수 없습니다.

**영향** — 현장 189건을 sites[].rawText 원문으로만 보존, sites[].dates 는 비움.

### 8. 업체별 변경 이력 / 업체 등록일

**사유** — 변경사항 내역 메뉴는 사이트 전체(코드) 변경 로그이며 업체 단위 이력이 아닙니다. 등록일 필드도 원본에 없습니다.

**영향** — changeHistory 전건 빈 배열, profile.registeredAt = null. 업체코드 규칙(YY+3자리)으로 추정되는 연도만 registeredYearFromCode 에 참고용으로 담았습니다.

### 9. 2024년·2023년 매출액

**사유** — 연도별 등급(2024/2023) 데이터의 sales 값이 전건 0 이며, 해당 메뉴는 등급 스냅샷만 담고 있습니다.

**영향** — sales 는 2025년 실적이 있는 업체만 포함(134건).

### 10. 업체별 교육·커리큘럼 이수 이력

**사유** — 통합 커리큘럼 메뉴는 프로세스 정의 문서이며 업체별 이수 기록이 없습니다.

**영향** — curriculumHistory 전건 빈 배열. 커리큘럼 정의는 meta.curriculum 으로 포함.
